SQL + NoSQL

You've shipped both — PostgreSQL in the La Liga pipeline, MongoDB in the World Cup pipeline. The risk isn't knowledge, it's rust: SQL screens are standard and unforgiving.

Why LSports cares Feed data has to land somewhere. Fixtures, markets and settlement need relational integrity and joins (MySQL/PostgreSQL); raw event streams at high write rates fit document stores (MongoDB). LSports job posts name MySQL, PostgreSQL and MongoDB explicitly.

The SQL you must write cold

Working schema for everything below:

fixtures(fixture_id, home_team, away_team, kickoff, competition)
events(event_id, fixture_id, minute, type, player)        -- type: 'goal','shot','card'
markets(market_id, fixture_id, name, price, updated_at)

JOIN + GROUP BY + HAVING — the classic screen question

-- competitions averaging more than 2.5 goals per fixture
SELECT f.competition,
       COUNT(*) FILTER (WHERE e.type = 'goal')::numeric
         / COUNT(DISTINCT f.fixture_id) AS goals_per_match
FROM fixtures f
JOIN events e ON e.fixture_id = f.fixture_id
GROUP BY f.competition
HAVING COUNT(*) FILTER (WHERE e.type = 'goal')
         > 2.5 * COUNT(DISTINCT f.fixture_id);

Remember the trap: WHERE filters rows before grouping, HAVING filters groups after.

LEFT JOIN and the NULL trick

-- fixtures with no goal at all
SELECT f.fixture_id
FROM fixtures f
LEFT JOIN events e ON e.fixture_id = f.fixture_id AND e.type = 'goal'
WHERE e.event_id IS NULL;

INNER JOIN drops non-matching rows; LEFT JOIN keeps the left side and fills NULLs — then IS NULL finds the "no match" rows.

Subquery / latest-row-per-group

-- current price per market: the newest row per market_id
SELECT DISTINCT ON (market_id) market_id, name, price, updated_at
FROM markets
ORDER BY market_id, updated_at DESC;
-- portable alternative: ROW_NUMBER() OVER (PARTITION BY market_id ORDER BY updated_at DESC) = 1

"Latest odds per market" is literally LSports' data shape — expect a variant of this.

Indexes — the two-minute theory

  • An index is a sorted structure (B-tree) that turns a full-table scan into a lookup: O(n) → O(log n). Cost: extra disk and slower writes (every INSERT/UPDATE maintains it).
  • It helps: WHERE fixture_id = 101, range scans (updated_at > ...), JOIN keys, ORDER BY on the indexed prefix.
  • It does not help: functions on the column (WHERE UPPER(name) = ...), leading wildcards (LIKE '%goal'), low-selectivity columns (a boolean), or a composite index queried without its first column.
  • Diagnosis tool: EXPLAIN ANALYZE — say those two words in the interview.

Transactions in one line each

ACID: Atomic (all or nothing), Consistent (constraints hold), Isolated (concurrent transactions don't see each other's half-work), Durable (committed = survives crash). Settlement — moving money on a final score — is the canonical "this must be a transaction" example at a betting-data company.

Your interview line "I've used both on my own projects: Postgres where I needed joins and integrity across fixtures and matches, Mongo where documents were nested and changing shape faster than I wanted to run migrations. For settlement-grade data I'd insist on SQL and transactions; for raw feed archiving a document store is fine."

Before any interview

  • Drill ~20 medium SQL exercises (joins, group-by, window functions). Rust, not ignorance, is what fails students.
  • Practice writing SQL on paper or a whiteboard — no autocomplete, no running it.
  • Re-read your own two pipelines' schemas so you can sketch them from memory.
