ETL that survives contact with reality

The interview question is never "can you write ETL" — it's "what happens when it breaks at 3am." Have opinions on:

  • Idempotent loads: re-running a failed job must not duplicate rows. Upsert on a natural key (INSERT ... ON CONFLICT DO UPDATE) or replace-the-partition, never blind append.
  • Retries with backoff: transient network/API failures get retried with exponential backoff and a cap — then fail loudly, not silently.
  • Dead-letter the bad rows: one malformed record shouldn't kill the batch; quarantine it to a reject file/table with the error, and alert on the rate.
  • Validate at the boundary: check schema and sanity (a shot at minute 137? xG of 1.4?) on ingest, before bad data spreads downstream.
  • Checkpointing: long backfills record progress so a crash resumes, not restarts.
Yours Your La Liga pipeline (PostgreSQL upserts, Docker) and World Cup pipeline (MongoDB event + sentiment ingestion) are your evidence. Re-read their code before an interview and pick one failure you handled to tell as a story.

Scraping and REST — the professional's checklist

  • Prefer the API when one exists; scrape HTML as a last resort.
  • Be polite: respect robots.txt and terms, rate-limit yourself, cache responses, identify with a User-Agent. Hammering a site is both rude and a great way to get blocked mid-project.
  • Expect drift: sites change markup. Isolate selectors in one place, validate outputs, alert when the shape changes instead of loading garbage.
  • REST semantics: GET is safe/cacheable, POST creates, PUT is an idempotent replace, DELETE removes; 2xx success, 429 Too Many Requests = back off (honor Retry-After), 4xx your fault, 5xx theirs → retry with backoff. Pagination and auth (API keys, tokens) are assumed knowledge.

Docker and tests — the credibility layer

  • Docker in one line: an image is a frozen recipe (code + deps + OS libs), a container is one running instance; compose spins up your app + Postgres/RabbitMQ identically on any machine. "Works on my machine" stops being a sentence you say.
  • pytest habits that show: small pure functions tested directly (your test_model.py), fixtures for shared setup, edge cases named in the test name (test_stoppage_time_winner_not_extra_time-style). Deterministic tests — no sleeps, no network.
  • Pandas performance instinct: vectorize (df["xg"].sum()), never iterrows() in hot paths; groupby/merge are your JOIN and GROUP BY in memory.
Yours live-pipeline/tests/ (model, pipeline, corpus) is proof you test real logic — including the honest back-test where the simpler model beats your production blend. Engineers reading that README trust everything else in it more. Keep tests green: run pytest before every push.
