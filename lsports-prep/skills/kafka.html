Apache Kafka

Named in LSports' requirements next to RabbitMQ, and currently missing from your portfolio. Different philosophy from RabbitMQ — learn the contrast and you've learned both better.

Why LSports cares Thousands of simultaneous live events, every message fanned out to many customers, with replay when something goes wrong downstream. That's high-throughput, multi-reader, replayable delivery — Kafka's home turf. LSports job posts list Kafka alongside RabbitMQ as a core requirement.

The mental model: a log, not a mailbox

RabbitMQ = mailbox. A message is delivered, acked, and deleted.
Kafka = newspaper archive. Messages are appended to a log and kept (hours, days, forever — per retention policy). Consumers don't remove anything; each one just remembers how far it has read.

  • Topic — a named stream (e.g. live-scores), like your exchange + key family.
  • Partition — a topic is split into N append-only logs. Partitions are Kafka's unit of parallelism and ordering.
  • Offset — a message's position in its partition. A consumer's state is just "partition 3, offset 4,182."
  • Consumer group — consumers sharing a group id split the partitions among themselves; separate groups each read the full stream independently.
topic "live-scores", 3 partitions (key = fixture_id):

p0: [f101 ev1][f101 ev2][f101 ev3]...   ← all fixture_101 events, in order
p1: [f102 ev1][f102 ev2]...
p2: [f103 ev1][f104 ev1][f103 ev2]...   ← two fixtures can share a partition

group "dashboard"  → reads p0+p1+p2, tracks its own offsets
group "archiver"   → reads the same data independently, at its own pace

Ordering — the rule that matters for sports feeds

Kafka guarantees order within a partition only, never across partitions. Messages with the same key hash to the same partition. So for a live feed: key by fixture_id → every event of a match stays in order, while different matches process in parallel. Key by nothing (round-robin) and a goal could be consumed before the kickoff event that precedes it.

Consumer groups and rebalancing

Group of 3 consumers, 3 partitions → one each. A consumer dies → Kafka rebalances, reassigning its partitions to the survivors, who resume from the last committed offset. Two consequences interviewers probe:

  • More consumers than partitions → the extras sit idle (partition count caps parallelism).
  • Redelivery: if a consumer crashed after processing but before committing its offset, the successor re-reads those messages → at-least-once delivery → consumers must be idempotent. (Same lesson as RabbitMQ acks, new mechanism.)

Kafka vs RabbitMQ — the interview answer

RabbitMQKafka
ModelSmart broker routes; message deleted after ackDumb log retains; consumers track offsets
ReplayNo (hence your snapshot RPC)Yes — rewind to any retained offset
RoutingRich (topic patterns, headers, per-queue bindings)Coarse (topics + keyed partitions)
OrderingPer queue, single consumerPer partition (per key)
ThroughputHighVery high (sequential disk I/O, batching)
Sweet spotTask queues, RPC, per-customer selective feedsEvent streaming at scale, many independent readers, replay/audit

Say it in one breath: "RabbitMQ when I need clever routing and per-consumer queues — like giving each sportsbook its own filtered feed. Kafka when I need massive throughput, multiple independent readers, and the ability to replay history — like feeding the same event stream to pricing, settlement and analytics. In my pipeline I used RabbitMQ and had to build a snapshot RPC for late joiners; with Kafka they could have replayed the log instead — that trade-off is exactly why you'd run both."

Your 1–2 week plan

  1. Run Kafka locally with one docker compose file (a single KRaft-mode broker — no ZooKeeper needed on modern Kafka).
  2. Add a Kafka transport next to RabbitMQ in live-pipeline/tradepipe/broker.py using confluent-kafka: topic trade, key = fixture_id, same JSON messages.
  3. Demo the two Kafka superpowers your RabbitMQ version lacks: start a second consumer group and watch it independently read the full stream; then reset offsets to 0 and replay a finished match.
