Real-time systems

The intellectual core of the job — and your strongest area. You've implemented every concept on this page in live-pipeline. The work now is rehearsing the vocabulary.

Why LSports cares A sportsbook showing a stale score, or missing a settlement message, loses real money in seconds. Correctness under speed — ordering, recovery, duplicates, slow consumers — is what separates a feed company from a CRUD shop, and it's what senior engineers probe in interviews.

The five concepts, with your implementation next to each

1. Message ordering (sequence numbers)

Networks and brokers can reorder or drop. The fix is a monotonically increasing sequence number per stream: the consumer tracks the last seq applied, so it can detect "I got 47 but expected 46."

Yours Every message in your pipeline carries MsgSeq; the consumer checks continuity per fixture (see live-pipeline/tradepipe/consumer.py).

2. Gap recovery (snapshots)

When a gap is detected (or a client joins late), replaying the entire history is slow or impossible. Instead: request a snapshot — the current authoritative state — then resume the live stream from there. The seam is safe because state + subsequent updates ≥ any missed messages.

Yours live-pipeline/tradepipe/snapshot.py — RPC on snapshot.<fixture> returning full MatchState, mirroring LSports' real Snapshot API for exactly this purpose.

3. Idempotency (safe duplicates)

At-least-once delivery (RabbitMQ redelivery, Kafka uncommitted-offset replays) means duplicates will happen. Processing must give the same result applied once or twice. Techniques: ignore seq ≤ last applied; make updates absolute ("score = 2:1") rather than relative ("+1 goal"); dedupe by message id.

Yours Your livescore updates carry absolute state, and seq tracking discards already-applied messages — say both of these out loud in interviews.

4. Backpressure (slow consumers)

A producer faster than a consumer will sink the system unless something gives: bound the buffer (queue limits, prefetch), shed load (drop stale ticks — a 3-update-old odds price is worthless anyway), or scale consumers. The unacceptable answer is an unbounded in-memory buffer.

5. State reconstruction (late joiners)

New subscriber needs current state, not a lecture on history. Patterns: snapshot + live stream (yours, and LSports'), or a compacted log holding the latest value per key (Kafka). Either way, the invariant is: state first, then updates with seq > snapshot's seq.

The follow-up questions, answered

"Message 47 arrives before 46. What do you do?"

Depends on the contract. If updates are absolute and independent (odds prices), apply 47, and when 46 arrives late, discard it (seq ≤ last applied). If updates are incremental or 46 might matter, hold 47 briefly in a reorder buffer; if 46 doesn't arrive within the window, treat it as a gap → request snapshot. Never apply 46 after 47 as if nothing happened — that regresses state.

"Your consumer restarts. How does it catch up?"

On startup it doesn't trust its stale memory: subscribe to the live stream, request a snapshot, apply the snapshot, then apply only buffered live messages with seq greater than the snapshot's. (Subscribing before snapshotting closes the race where a message lands between the two.)

"How do you know your feed is healthy when nothing is happening?"

Heartbeats: your pipeline's KeepAlive (MsgType 31) — silence then means connection dead, not match quiet. Monitor end-to-end latency and per-fixture seq gaps, not just process uptime.

  2. For each of the five concepts, say the one-line definition + where it lives in your code.
  3. Have a war story ready: a bug you hit (ordering, duplicate, reconnect) and how you fixed it — concrete beats abstract.
